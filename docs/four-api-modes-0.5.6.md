# Distinct fourth booking mode — 0.5.6

The public form already listed four handoff choices, but deployed plugin 0.5.5 exposed only three `modes` and rejected `prepaid_pickup_delivery` in the portable API. Two `handoff_options` shared `prepaid_pickup` with different return fields. Clarifying Markdown did not remove that ambiguity for clients constructing a menu from the mode list.

Backend 0.5.6 advertises four independently selectable modes in `/booking-options` and `/capabilities.booking`. Both endpoints share the same handoff-menu helper, with live transport prices and ZIP/payment flags. The fourth mode is `prepaid_pickup_delivery`; it implies `return_mode=courier_delivery` when absent and rejects an explicitly conflicting customer-collection value.

Normalization stores the existing canonical `prepaid_pickup` plus `courier_delivery` format before coverage validation, fingerprints, idempotency or checkout. Old composite requests and new fourth-mode requests therefore share one equivalent draft for the same owner/key. Existing native orders, quoted prices, address/payment consent and refund accounting are not migrated. The fourth mode still requires eligible pickup coverage, human contact approval and verified native payment before merchant submission.

OpenAPI 1.6.0 defines the four-mode input, the fourth-mode return constraint and typed four-entry booking discovery. The skill source declares 0.5.6 and documents the direct mode plus legacy compatibility. Registry publication remains 0.4.2; no new ClawHub audit or certification is claimed. No host bot installation or runtime context is controlled from this chat.

Validation must use the fenced synthetic database and blocked outbound mail/HTTP. The four-option suite now exercises actual REST discovery and fourth-mode draft creation, the omitted delivery default, $11 transport, equivalence with the old idempotency representation, conflicting return rejection and denied pickup coverage. Its full native quotation/submission path uses the fourth alias. Run existing listing, booking, bridge, lifecycle and four-option suites in classic/HPOS with synchronization on/off. Validate actual response samples against the contract; lint/package before native production update. Do not charge or refund a real order or create a production test booking.
