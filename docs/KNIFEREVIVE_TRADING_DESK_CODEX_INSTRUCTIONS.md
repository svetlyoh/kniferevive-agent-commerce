## 2. Product model and automatic classification

- Trading Desk is a marketplace-wide sourcing service, NOT a product category. A Trading Desk Apple Watch still belongs to Tech; a knife remains in its knife category.
- Every listing imported from Facebook Marketplace must automatically receive the Trading Desk designation, regardless of whether the source seller has responded. Extend the data model generically to support other external sources without a Facebook-specific schema. Do not label independently owned inventory by default.
- Automatically initialize source marketplace, source listing ID, source URL, discovery timestamp and other source details actually supplied by the importer. Never invent missing values. Import into draft/review rather than automatically publishing unapproved third-party material.
- Separate **source provenance** (permanent history) from **current fulfillment mode** (standard or Trading Desk). When the item is acquired, allow an authorized operator to explicitly convert it to standard inventory after confirming possession, condition, quantity, fulfillment readiness and price. Preserve sourcing history. Subsequent imports/updates must not reset an explicitly acquired item to Trading Desk.
- Do not treat a seller's availability confirmation, a reservation, or an agreed price as physical acquisition. Do not infer possession from WooCommerce stock quantity.
- Backfill previously imported listings using reliable existing source IDs, URLs or importer metadata. Provide a dry-run report and explicit review for ambiguous products; do not infer provenance from photos or descriptions. Preserve documented acquired items. Make migration idempotent; prevent known unacquired imports from remaining directly purchasable during rollout. Re-running import should not duplicate a seller's existing source listing or erase manual data.

## 3. ListLab editor: visible toggle and private sourcing workspace

In the create/edit listing screen, add a compact **Trading Desk** switch with an explanation: “This item is held by another owner. Buyers request it instead of purchasing immediately.” Default off for ordinary manually created listings; on automatically for external imports. Permit authorized manual designation for offline sourcing too. Restrict toggling off for externally sourced items to the explicit acquired/standard conversion workflow; no accidental bypass. The control is seller/operator-facing, not a public buyer toggle. Preserve normal listing UX when disabled.

Add a collapsible **Sourcing & Seller Communication** section, automatically initialized and shown for imported listings, available for any listing with sourcing history even after conversion. For manually created standard listings, keep the section collapsed/optional. Reuse existing form layout, save/discard behavior, loading states and mobile styling. All fields below are private unless specifically marked public in section 5. Do not require irrelevant fields for ordinary products or incomplete drafts.

### Private field specification

| Group | Fields and behavior |

| Availability and logistics | Availability status (unknown, seller-confirmed, reserved, unavailable); last confirmed timestamp; reservation expiry if applicable; fulfillment arrangement (pickup, ship to KnifeRevive, other agreed arrangement); acquired/possession confirmed timestamp; private status notes. |

Use timestamps in a consistent canonical timezone (UTC recommended), render in the operator's site timezone, store currency as ISO code and money as validated decimal strings. Keep unknown optional values null. No fake timestamps or automatic verification merely because a field exists.

### Repeatable question-and-answer trail

Build a dedicated **Questions & Answers** subsection, not one combined textbox. ## 6. Request-first purchasing (mandatory safety boundary)

A Trading Desk product is not normal available stock. Display a price as an indicative/listed price, not a confirmed offer where availability or acquisition is uncertain. Do not misleadingly display “in stock” or guarantee delivery. Preserve WooCommerce product discovery even if normal stock visibility would hide these products; use public-safe mode-aware queries and presentation, not fake inventory.

Prevent direct purchasing on the server, not merely by hiding buttons. Cover single product forms, catalog AJAX, direct add-to-cart links, WooCommerce Store API/cart blocks, existing carts and checkout/order creation paths. Revalidate mode at checkout to handle stale carts and concurrent changes. Use supported WooCommerce hooks and current source; never edit core. Prevent price/stock changes from reopening checkout while mode is Trading Desk. Disable incompatible express-payment buttons. Normal products must continue working unchanged.

Implement a request workflow using existing authenticated buyer/account features where possible:
1. Buyer clicks Request to Buy; display a simple form with item, indicative price, optional note, and clear no-payment explanation. Require login or use an existing secure verified-contact mechanism; initial recommendation: existing My Account login.
2. Create a private request record with buyer ID/contact reference, product ID, price snapshot/currency, timestamps and status. Do not create a payable order, charge, reserve stock, or collect payment here. Protect against duplicate submissions, spam and unauthorized access; return a clear confirmation.
3. Notify authorized KnifeRevive operator through existing notification infrastructure; provide an operator queue/list linked to the sourcing record, and buyer-facing request status. No exposure of original seller contact to buyer.
4. Operator contacts owner, confirms current availability/price, and attempts acquisition. Request statuses: New, Checking Availability, Secured, Purchase Invitation Sent, Completed, Unavailable, Cancelled. Handle multiple requests without promising one unique item to several buyers.
5. Once item is physically secured and inspected/ready to fulfill, operator explicitly converts to standard inventory and issues a buyer-specific purchase invitation using supported WooCommerce flow. A secure buyer-specific reservation and checkout handoff is mandatory for public launch; see section 6A. If blocked, document the dependency and keep the public feature disabled; never enable unrestricted payment to simulate it. Confirm final price, shipping, applicable policies and buyer acceptance before payment. Record the link between request and resulting order when implemented.
6. If unavailable or price changes, notify buyer honestly; no payment to refund at request stage. Close or update requests appropriately and stop accepting requests on unavailable listings.

Do not implement automatic messaging to Facebook, automatic acquisition, scraping, payment authorization/escrow or delivery guarantees as part of this change. Do not enable a live public CTA unless request persistence, permissions, operator notification and no-payment behavior are functional. If necessary ship the internal editor first behind a feature flag.

### 6A. Complete buyer-to-operator request workflow (expanded mandatory scope)

Treat this as a complete two-sided feature, not a button, contact form, or future placeholder. The public feature must remain disabled until the buyer, operator, notification and protected purchase-invitation paths are working end to end. The Trading Desk operator is the KnifeRevive listing owner or an authorized manager; the original external owner is not automatically a KnifeRevive seller or a participant in the site workflow.

**Buyer experience**

1. Request to Buy opens a mobile-friendly form showing product photo/title, indicative price/currency, availability disclaimer, optional buyer questions or preferred delivery method, and the buyer's existing account/contact information. Initial recommendation: require existing account login, return to the same item after sign-in, and avoid re-entering known details. CTA: “Send request”. Copy: “No payment yet. We'll check with the owner and get back to you.” A request is not an order, reservation, payment or commitment.
2. On successful submission, show a persistent confirmation with request reference, status, link to My Account → My Requests, and copy: “You're on our radar. We'll check if this one's still available and message you here.” Send a transactional acknowledgment via existing email infrastructure. Do not promise a response deadline unless operationally supported.
3. Add My Requests to existing buyer account navigation, with request list and detail/timeline: item, submitted price, status, updates, buyer-visible messages, any questions needing an answer, final offer, and next action. Allow buyer reply and cancellation before purchase (after purchase use order support/policies). Do not expose private source notes or original owner contact.
4. When more information is needed, show a clearly actionable question from KnifeRevive and allow the buyer to reply in the request thread. Send an email with a secure account link; keep conversation history. Buyer may withdraw without payment or penalty before an order is placed.
5. When the item is secured, present a buyer-specific purchase invitation with final item price, shipping/tax calculation or clear estimate, condition/inspection and included items, applicable returns policy, fulfillment estimate if established, and offer expiry. Make any price difference from the original request explicit. CTA: “Review & Buy”. Buyer must actively accept the final terms and complete normal WooCommerce checkout; never charge automatically. If buyer declines or invitation expires, close/release the reservation and inform the operator.
6. After checkout, show order number and link to normal WooCommerce order details; continue using existing order, fulfillment, tracking and return flows. Unavailable items: notify buyer and close request with a clear reason, no payment collected. Optional alternatives may be suggested manually; never substitute without buyer approval.

**Operator experience**

Add Trading Desk Requests to the existing seller/operator workspace (prefer a dedicated ListLab view or My Account endpoint following current navigation conventions). Show unread/new count, request age, product, buyer, status, last update, and next action; filter by status and search by request ID/product. Detail view links to the private sourcing record and has a buyer-facing message thread distinct from internal notes. Provide actions to acknowledge, check availability, ask buyer a question, record external-owner confirmation, mark unavailable, mark secured, create/send purchase invitation, cancel, and open resulting order. Only authorized listing owner/managers may see or operate requests; external sellers have no access unless separately authorized under a later design.

Before offering purchase, require an explicit verification checklist: current owner availability and timestamp; final acquisition price and currency; exact item/model/condition and included accessories; unresolved defects/questions; permission to market and use images; acquisition/fulfillment plan; final buyer price, shipping and applicable return terms. Record evidence and outcome privately; never mark independently inspected without actual inspection. For initial release require physical acquisition/inspection and readiness before checkout, as specified above; if unavailable, mark product accordingly and notify all affected pending buyers. Capture the operator's action and timestamp. Do not automatically contact Facebook or send external-owner messages; operator handles this manually.

**State machine and communication**

Use explicit server-side transitions (names may adapt to existing conventions): New → Checking Availability ↔ Awaiting Buyer Reply → Secured → Offer Sent → Purchased. Terminal outcomes: Unavailable, Buyer Cancelled, Operator Cancelled, Offer Expired/Declined. Allow return from Awaiting Buyer Reply to Checking Availability; a new offer requires a new explicit acceptance. Separate product sourcing state from per-buyer request state. Store request ID, product/seller/buyer IDs, indicative price/currency snapshot, final quote and revision, expiry, linked order ID, timestamps, immutable status/audit events, and scoped messages with author/time/visibility. Only buyers may read/reply to their own requests; authorized operators may act on assigned requests. No arbitrary status writes from client; validate transitions, nonce/capability, ownership, message length and rate limits. Use idempotent actions and handle concurrent edits.

Trigger transactional notifications on new request (operator and buyer acknowledgment), operator reply/question, buyer reply (operator), purchase invitation, unavailable/cancelled/expired and order completion as appropriate. Use existing WordPress/WooCommerce mail infrastructure; secure links to request details, no private source data, avoid duplicate sends on retries, record delivery attempts/failures and provide manual resend. Do not assume WhatsApp automation is available. Buyer-visible timeline is authoritative even if email fails.

**Protected WooCommerce purchase handoff**

For a unique item, maintain one active buyer-specific reservation/invitation at a time. The buyer-exclusive purchase window is 72 hours (three full days), starting when the operator enables purchase and the invitation is issued, not when the initial request is submitted or the original seller is contacted. Persist the authoritative issuance and expiry timestamps in UTC; display the expiry in the buyer’s local time. The invitation email and My Requests must state the deadline and link to the canonical product page. On that same main listing, the authorized signed-in buyer sees Buy Now/Add to Cart during the active window; all other visitors see Reserved and may join the request waitlist. After 72 hours, if no purchase has completed, expire the invitation and release the exclusive reservation; the operator may invite the next buyer or explicitly open the listing to everyone only if physically acquired and ready to fulfill. Do not automatically open public checkout on expiry. Recheck expiry server-side at cart and checkout, including stale sessions; define safe handling of already-created pending-payment orders to avoid double allocation. The operator may revoke an invitation early if availability changes; notify the buyer. A replacement invitation requires an explicit new operator action and a new 72-hour window. Multiple requests may be received but no double promises; show other requests as waiting until item is released or sold. On acquisition, preserve source record and explicitly mark physically acquired. Use a supported WooCommerce buyer-bound checkout mechanism with server-enforced buyer/product/price/expiry/stock checks; an invitation link alone is not authorization. If converting product to standard inventory before payment, keep reservation lock enforced across catalog, direct cart URLs, AJAX, Store API, stale carts and checkout for all other buyers. Do not use fake stock or public coupon links as the security mechanism. Create a normal order only on the authorized purchase path; maintain idempotent request-to-order association, prevent duplicate orders or charges, and release/close reservations on decline/expiry or according to existing failed-payment policy. Handle tax, shipping, payment and order state via existing WooCommerce mechanisms. If a secure handoff cannot be implemented, report the blocker and keep the public end-to-end feature disabled rather than silently substituting unrestricted Add to Cart.

**Additional acceptance tests**

- Normal product purchase flow and existing seller order/fulfillment/inspection behavior are unchanged.
